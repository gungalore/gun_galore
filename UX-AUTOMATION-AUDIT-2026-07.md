## Quick wins (63)

### 1. Show the search query on the results page
- **Impact:** high · **Slice:** home-browse · **Category:** ux · **File:** `frontend/app/page.tsx`
- **Problem:** Searching "glock" lands on /?q=glock which is headed "Live listings — Everything on sale right now..." with an EMPTY search box (LiveSearch keeps its own state, never seeded from the URL). The user has no visible confirmation of what they searched, can't edit the term without retyping it, and the browser tab title also ignores the query.
- **Fix:** As proposed, plus one detail: the empty search box appears via FilterBar's embedded LiveSearch, so thread the prop as FilterBar currentParams.q → LiveSearch defaultValue (initialize useState(defaultValue ?? '')). Since LiveSearch is remounted per server-rendered navigation this stays simple; also handle q in generateMetadata (`Results for “{q}” — Gun Galore`) and in the h1 for both DEFAULT_SURFACE and typed-surface cases (q + listingType=AUCTION currently shows just 'Auctions' too).

### 2. Keep the active surface/filters when searching
- **Impact:** high · **Slice:** home-browse · **Category:** ux · **File:** `frontend/components/live-search.tsx`
- **Problem:** A user browsing Auctions (or a category) who types into the search box and presses Enter is pushed to `/?q=term` — LiveSearch.onSubmit and the "See all results" footer both discard listingType, categoryId and every other active filter. Their scoped browse silently becomes an all-site search.
- **Fix:** Reviewer's fix is right. Implementation note: give LiveSearch an optional `preserveParams?: Record<string,string>` and build the target with `new URLSearchParams({...preserveParams, q: term})`; FilterBar passes at minimum listingType and categoryId from currentParams (arguably all non-page filter params — searching within filters is the intuitive behavior, and the page-1 reset happens naturally since page isn't passed). Nav and drawer usages pass nothing and keep global behavior.

### 3. Distinguish API failure from an empty marketplace
- **Impact:** high · **Slice:** home-browse · **Category:** ux · **File:** `frontend/app/page.tsx`
- **Problem:** apiFetch for /listings is caught and collapsed to `{ listings: [], total: 0 }` (page.tsx line 142-144). If the backend hiccups, browse surfaces render the genuine-empty copy "Nothing listed here yet — got one lying in the safe or the garage?" and the bare landing silently loses its entire "Latest listings" grid — the live site reads as a dead site, with no retry affordance. app/error.tsx already exists but never fires for this path.
- **Fix:** Cleanest: catch into a sentinel (`.catch(() => null)`) and where browse === null render a 'We couldn't load listings right now' card with a retry link (same href) instead of the empty-marketplace copy; on the landing page render the same small card in place of the Latest-listings grid rather than nothing. Rethrowing to error.tsx is heavier-handed — it would blank the whole page including the hero/featured sections that may have loaded fine.
